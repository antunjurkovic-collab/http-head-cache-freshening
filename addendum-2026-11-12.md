# Qualification and implementation update: HEAD freshening

Date: 12 November 2026

Status: Informational addendum to v1.0

This note qualifies the validator-free claim in the Abstract, Section 2 and
Section 8 of [HEAD Freshening and Stored-Response Association, v1.0](https://github.com/antunjurkovic-collab/http-head-cache-freshening/blob/v1.0/report.md).
It also adds later implementation evidence to the Abstract and Section 6.
The v1.0 release remains unchanged.

## Current assessment

The validator-free trace does not establish a defect in
[RFC 9111 Section 4.3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.5).
It depends on treating the absence of received validators as satisfying the
validator condition. Requiring at least one received matching validator
prevents the update; equal Content-Length is not a validator match.

The local test below establishes implementation behavior, not permission
under the RFC. A failure of a conforming cache has not been demonstrated.
This qualifies the Abstract's request for explicit treatment of the
zero-validator case and Section 8's call for clarification: no specification
change is requested on this evidence alone.

The original report contained no runtime reproduction in a cache
implementation. The later test adds one local reproduction in a pinned
Bouine revision, not evidence of occurrence in production deployments.

## Local implementation result

On 8 November 2026, an HTTP/1.1 test used unmodified Bouine source at commit
`81f02058a8b9c8b568fa6a88ccad7abb649becbc`. Two separate paths under the
same cache configuration provided matched HEAD and GET cases:

1. Cache `AAAA` with `max-age=2`, without ETag or Last-Modified, and
   confirm an immediate GET cache hit.
2. Change the origin to same-length `BBBB` with `max-age=600`, still
   without validators, and wait 3.2 seconds.
3. Send an unconditional HEAD on one path and an unconditional GET on the
   other, then GET each path again.

After HEAD, the next GET returned cached `AAAA` with `max-age=600` and
`Age: 0`. The GET control fetched `BBBB`, which its next cache hit also
returned. Captured origin exchanges confirmed both refresh methods and
that neither subsequent cache hit contacted the origin.

Bouine's [headFreshenAllowed function](https://github.com/bouine-cache/bouine/blob/81f02058a8b9c8b568fa6a88ccad7abb649becbc/internal/cache/handler.go#L3550)
compares validators only when present. That explains the observed behavior;
if a matching validator is required, this update is an implementation bug.

Bouine also sent `Content-Length: 0` downstream on HEAD, although the origin
sent `4` and the later GET carried four bytes. A supplied HEAD length must
describe the corresponding GET content, not the empty HEAD body.
[RFC 9110 Section 8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6).
The first attempt stopped on this discrepancy before completing the GET
control. The completed attempt checked the origin's HEAD response and
retained the downstream discrepancy; Bouine and the origin scenario were
unchanged.

## Limits

There was one completed matched run. HEAD without Content-Length was not
tested. The experiment's harness and captures are not included in v1.0.

This update concerns validator-free freshening. It does not validate or
withdraw the separate field-input, Vary-association and omitted-Vary
observations. The Vary overlap with earlier 304 work is not a distinct
failure class, and the report's candidate restrictions remain unvalidated
as a complete repair.
